# Agent CLI design

Exit codes, envelope, paging and flags follow the owner's Agent-First CLI guide. Code 9 and the omitted `--profile`/`APP_TOKEN` are the only deliberate departures, each justified below.

Decision: ship a thin BCL-only `luatools` console client connected to an authenticated local named pipe hosted by the **single running GUI owner**. A typed `AgentCommandService` facade invokes the GUI's existing DI singletons and shared operation coordinators. The client parses commands, negotiates protocol/context, renders DTOs and manages deadlines. It never opens settings, cache, auth, vault, Cabinet, receipt, queue-history or event-log files, constructs a second service container, or implements acquisition/install/business rules. It may read owner discovery and explicitly supplied input files. There is no offline-state fallback.

The feasibility spike measured silent settings/cache lost updates in 3/3 stale-snapshot trials. Independent processes therefore remain forbidden even if they use unique temporary files or a file lock around replacement. The GUI owns all state reads/writes, auth refresh, process identity, queue dedupe and install serialization. Keep its existing dispatcher; snapshot/enqueue on it briefly, then await disk/network/completion off it. Never resolve arbitrary services or forward arbitrary plugin routes over the pipe.

This is a reviewed design, not an implemented CLI. The [capability map](capability-map.md) is the traceability ledger: 256 inventory rows, four legacy routes and one declared/unbound command, with compound branches split before deduplication. Its statuses distinguish reusable operations, required extractions, presentation exclusions and owner-reserved operations. Only the two documents are repository deliverables. Review was static against all five inputs and selected source; Windows behavior remains unverified.

## Command grammar and complete resource tree

Use `luatools <resource> <verb> [identity] [flags]`. Resource names use singular GUI vocabulary, kebab-cased where needed: `game`, `lua`, `preset`, `depot`, `launch-option`, `fix`, `manifest`, `dlc`, `source`, `download`, `history`, `mode`, `cloudredirect`, `cloud-save`, `plugin`, `tool`, `setting`, `steam`, `account`, `hubcap-key`, `cabinet`, `cabinet-cloud`, `update`, `application`, `activity-log`, `link`, `onboarding`. `job` is the cross-resource operation handle. Standard verbs are `list`, `get`, `create`, `update`, `delete`, `search`; use only meaningful ones. Domain verbs such as `add`, `apply`, `revert`, `restart`, `download`, `sync` and `login` keep the GUI's meaning. Do not force installation into CRUD or invent deletion for read-only catalogues.

Brackets and the `|` characters in this grammar express optional/exclusive arguments, not shell pipelines. Omitted identity placeholders in the ledger are illustrative: `game get` still requires an App ID or supported link. A depot update always carries its parent App ID. `preset` identity is content hash plus App ID, never mutable display name. A fix ID is provider-scoped; include `--provider` and `--appid`. DLC IDs and Steam App IDs are validated by existing contract/parser rules, with stricter positive bounds where that path already requires them. Never accept an arbitrary URL to a download or an arbitrary executable path.

`--file` accepts an explicit existing Windows path readable by the GUI owner; the client submits a bounded byte payload with original base filename, length and SHA-256, using chunk frames for manifest/ZIP inputs above the control-frame bound. The host validates/hashes it again and uses the original filename for installer identity rules. It stages inside its own bounded input directory, validates reparse/path safety, and calls the existing path-based service. This avoids opening arbitrary host paths via a generic RPC and avoids file-replacement races after confirmation. Lua add supports at most 64 files per request, total bytes bounded by existing content limits and an advertised host staging budget. Validate before staging; remove unused staged bytes on rejection/expiry. No client-supplied staging/output paths bypass the existing path policy. Depot output is necessarily an explicit, contained workflow-specific path, not a generic filesystem API. Large files fail promptly on limits/space; do not buffer unbounded base64 JSON. Implementation must not write to full `/tmp`; Windows uses the owner's validated local staging root.

CLI `game get` returns metadata, IDs, paths, related URLs and action hints. GUI Copy App ID becomes `--fields id`, Reveal becomes `--fields paths`, and store/library navigation becomes `--fields urls`; these are deliberate read mappings with no clipboard/Explorer/browser access. `game install` is different: it asks Steam's native installer through the fixed `steam://install/<id>` handoff, so it changes state and requires confirmation. Return `handed_off`, never pretend a Steam download completed. If the selected Steam isolation cannot be proven for that protocol handler, disable it rather than launching another installation.

No `page` or `view` RPC resource is needed: Page maps to resource pagination and persisted page-size settings; View holds seven explicit presentation exclusions. Navigation, flyout/results/banner/modal dismissal, filter-panel visibility, tile selection, drag hover, unsubmitted-editor/picker cancellation and window/tray chrome have no headless state to mutate. The map lists every original location, including unbound `CloseResultsCommand`, hidden bot banner and retained OpenWebsite. There is no generic window-control, clipboard or open-shell command. `link get` returns a policy-approved source invitation, website, Markdown or SteamDB URL as data. `--url` only validates an existing description link under `SafeMarkdown` policy; it is not an arbitrary browser-launch endpoint.

Queries are explicit and do not mutate GUI search, filters, current page or selection. Installed filters combine with AND; missing cached metadata is excluded while any category filter is active. Preserve GUI price/content choices, sort order and missing-last behavior. `fix --my-games` means Lua-added IDs, not Steam ownership. A clear-filters invocation simply omits category arguments. Read-only metadata warming may update a rebuildable cache; it never spends a download quota. Separate `depot reconcile` performs GUI selection/refresh's vault sync, loose-build adoption and possible auto-apply; normal depot/preset reads never call it. Mode detection is returned as `detected_mode` until explicit `mode update` persists selection. Launch-option get reads without `LaunchModStore.Rebase`; stage/apply owns necessary rebase.

## Flags, output and discovery

All RPC commands accept these global flags. Discovery/help/version parse them consistently; mutating-only flags on a read produce a usage error rather than suggesting a side effect occurred.

- `--json`: alias for `--format json`, one envelope on stdout, no banners, ANSI, progress or logs.
- `--format json|jsonl|csv|table|text`: default table on a TTY and json with redirected stdout. jsonl is required for watch/session streaming; watch plus `--json` emits one independently valid JSON envelope per line. `--json` and an incompatible explicit format are a usage error.
- `--fields <a,b,...>`: projection of `data` fields only, with nested dotted paths and allowlisted names from describe. Keep `ok`, `page`, `warnings` and `error` intact. Unknown/private fields fail; projection cannot select secrets. Server projects large results before framing.
- `--dry-run`: validate/plan a mutation without acceptance, acquisition, quota use, writes, process action or publication; details below. Unsupported planning returns `DRY_RUN_UNSUPPORTED`, not a live call.
- `--yes`: explicit consent to the submitted plan's enumerated overwrite/delete/quota/sharing/restart effects. It never disables gates or enables executable consent. Use `--plan-id` for previously reviewed plans; otherwise the host derives one bounded plan from explicit operands before committing.
- `--no-input`: never read a prompt or start unsolicited browser/dialog interaction. Implicit when stdin or stdout is redirected or in session mode. With neither consent nor an explicit decision, return `CONSENT_REQUIRED` and a plan. An explicit `--secret-stdin` or `--code-stdin` is input data, not a prompt; it can be used under no-input, including from redirected stdin. Reject secret-stdin in a multiplexed stdio session; use its dedicated secret frame or a separate invocation.
- `--read-only`: reject commands whose selected branch changes state or accepts work. Enforced in both parser and host/session, including aliases and batched requests; cannot be cleared inside a read-only session. Rebuildable metadata caching and observational DLC check handles are allowed; update check is denied because it stages/prunes packages; downloads, Steam stop/restart, job decisions, pause/cancel, reconcile and setting writes are denied. Existing GUI/background tasks continue independently; this flag is not a global freeze.
- `--quiet`: suppress human progress/success chatter. Never suppress requested JSON, failures, warnings requiring action, job IDs or a consent plan.
- `--verbose`: safe client transport timings and correlation diagnostics on stderr; never request payloads, auth headers, secret inputs or decrypted discovery. Conflicts with quiet.
- `--no-color`: disable ANSI in human output, also respect `NO_COLOR`. Machine formats never contain color.
- `--timeout <duration>`: one end-to-end call/wait deadline; default 30s for RPC, 250ms local pipe connect cap within it, and 5m for explicit job wait. Maximum 24h for wait/watch, bounded connection/read deadlines regardless. Timeout after acceptance does not cancel the job. Return accepted ID when known and `outcome_unknown` when acknowledgement was lost.

Additional operation flags: `--data <json|@file|->` supplies complex input for any create or update, validated against the schema, with flags overriding keys; `--ids a,b,c`, `--ids-from -` and `--where key=value` select bulk targets and always support `--dry-run`; `--if-version <value>` rejects an update when the target changed since the last `get` (exit 6, `VERSION_CONFLICT`); `--actor-note <text>` records who asked in the activity log; `--idempotency-key <key>` makes a mutation retry identifiable; `--plan-id <opaque>` binds consent to a reviewed plan; `--restart-steam` authorizes stop/restart only for an operation that needs it; `--keep-files` or `--delete-created` resolves depot cancellation; `--limit`, `--cursor`, `--all`, `--count` and `--sort` control lists; `--cursor` resumes a watch. These do not add alternate business paths. `--yes` alone cannot authorize hidden process shutdown: include `--restart-steam` unless the verb itself is `steam restart`. `--apply true` on launch-option update likewise needs the restart flag if selected Steam is running.

Guide flags `--profile`, `--account`, `--workspace`, `--endpoint`, a remote `--host` and `APP_TOKEN` do not apply. There is one local same-user GUI owning profile, selected Steam and auth; accepting them would create competing owners or credential paths. Replace them with `whoami`, `steam get` and `status`, plus `--expect-instance <nonce>` and `--expect-steam <opaque-identity>` guards for automation. Every mutation carries the discovered expected Steam identity even without a flag; optional flags pin a previously observed context across invocations. Changing selected Steam is a dedicated `steam update`, validated against the old identity and returning a new one. No `--enable-executables`, `--force` security bypass, password flag, token export/import or environment-secret alternative exists. Pipe capability discovery is automatic and independent of account auth. Universal shell completion/install flags are distribution ergonomics, not v1 capability gates.

`commands --json` returns a versioned descriptor array: resource/verb, syntax, aliases, schema, required identities, read/mutation class, dry-run support, implementation status, job behavior, exit/error codes and capability-map IDs. It describes **all** target commands, explicitly disabled with `NOT_IMPLEMENTED`, `REFACTOR_REQUIRED` or `OWNER_DECISION` until ready. `describe <resource>` returns input/output schemas, field enums/defaults, actions, preconditions, secret-channel requirements and examples without secrets. Both can show compiled grammar when GUI is absent, with `runtime_available:false` warning; runtime availability must be queried from the host before execution. Help/version are always local; ping/status/whoami require authenticated host contact. `ping` tests protocol readiness. `status` includes GUI instance/protocol, selected Steam identity, queue/helper counts, capability readiness and server health. `whoami`/`account get` return guest/authenticated, safe display name, provider, expiry state and local owner/elevation/session match, never access/refresh tokens, email/avatar by default or a credential-file path.

Settings describe lists effective types/defaults/allowed values, including nullable System language, DNS Auto/Always/Never, page sizes and immutable fork policy. Only GUI-owned allowlisted keys can change. `SelectedMode` uses mode update; `SteamPathOverride` uses steam update; `HubcapApiKey` uses secret provisioning; `DonateKeys` is always false and read-only. GUI paging preferences accept Manage/Fixes 12/24/48/0 and Depots 10/17/25/50/0; CLI page size is independent. Eight executable consent keys are readable and may be revoked with `setting update ... --value false`; true always fails `EXECUTABLE_CONSENT_REQUIRED` with the human GUI path. This is server enforced, including session/batch/file inputs.

Use stable IDs, booleans, integer byte counts and RFC3339 UTC timestamps; localized relative labels are presentation only. Non-ASCII names stay UTF-8. `page` is null for scalar results; list commands return `{limit,next_cursor,has_more,total}`. Default `--limit` is 50, maximum 200. `--cursor` resumes a list, `--all` fetches every page within response bounds, and `--count` returns only the total. Each list has a documented default sort and accepts `--sort`, so the same input gives the same order. Cursors expire after five minutes and reject changed snapshots rather than silently skipping items. `list` returns summary fields and clips long text with a marker; `get` returns full detail. GUI page-size settings stay GUI preferences and never affect CLI paging. Metadata, source and catalogue pages are bounded independently of provider responses.

## JSON envelope and failures

A success is `{ok,data,page,warnings}`. `warnings` is an array of `{code,message,details}`, empty when there are none. A failure is `{ok:false,error}`, written to stdout with `--json`, with one short line on stderr. List results put an array in `data` directly; operation metadata includes request and instance IDs inside `data`. Human messages come from EN/FR RESX and the maintained accessor; wire codes and field names are invariant. Never serialize raw exceptions or log strings as a contract. Every failure reports all validation problems at once in `error.problems`, each with its `field`.

```json
{"ok":true,"data":{"job_id":"queue-item-id","state":"queued","request_id":"uuid","instance_id":"nonce","deduplicated":false},"page":null,"warnings":[]}
```

```json
{"ok":false,"error":{"code":"STEAM_RUNNING","exit_code":6,"message":"Close the selected Steam instance or explicitly authorize its restart.","hint":"Run 'luatools steam get', or retry with --restart-steam --yes","retryable":false,"required_flags":["--restart-steam","--yes"],"action":"mode.update","request_id":"uuid"}}
```

Errors include code, exit_code, localized message, hint, retryable, and field and allowed values where relevant, plus bounded structured details: disabled actions, missing gate, per-item outcomes, plan or accepted job ID, never secrets or raw upstream bodies. Path fields are narrowly scoped to requested user resources; redact profile/account names from diagnostics. `retryable:true` means a deliberate retry may help; it never grants permission for automatic replay of a mutation.

Exit codes are stable and follow the guide's 0-8 contract. Code 9 is the one addition:

- **0**: success, or an accepted asynchronous job. Acceptance is not installation success.
- **1**: general or unexpected failure. Includes a job that `job wait` saw fail or be cancelled (`JOB_FAILED`, `JOB_CANCELLED`) and bulk partial failure (`PARTIAL_FAILURE`, with `data.results` per item).
- **2**: invalid usage: bad flag, missing argument, invalid value, unknown field or invalid ID format.
- **3**: not found: `NOT_FOUND`, `JOB_EXPIRED`, `PLAN_EXPIRED`, expired snapshot or cursor. Check the ID, then list or search.
- **4**: auth missing or expired: `LOGIN_REQUIRED`, missing, rejected or expired Hubcap key. Ask the human to run the login or key step.
- **5**: permission denied; stop and ask the human: `EXECUTABLE_WORKFLOW_DISABLED`, `EXECUTABLE_CONSENT_REQUIRED`, read-only refusal, pipe identity or elevation denial, `OWNER_DECISION`, `NOT_IMPLEMENTED`, `REFACTOR_REQUIRED`.
- **6**: conflict or failed precondition; re-read state, then retry: `STEAM_RUNNING`, `PLAN_STALE`, `REQUEST_ID_CONFLICT`, `VERSION_CONFLICT`, changed context, already applied, job already active.
- **7**: rate limited or temporarily unavailable: `QUOTA_EXHAUSTED`, `BUSY`, `TIMEOUT`, transport failure, uncertain acknowledgement (`OUTCOME_UNKNOWN`). `retry_after` is included when known. Never replay a mutation blindly: reconcile by idempotency key first.
- **8**: confirmation required: `CONSENT_REQUIRED`. The error carries the plan and its impact. Confirm with the human, then add `--yes`.
- **9**: `GUI_NOT_RUNNING`, an addition for this architecture: missing or stale discovery, or no owner pipe. Waiting does not help, so it is not code 7. Start LuaTools, then retry.

Ctrl-C during `job wait` exits 130 and leaves the accepted job running. A killed process can bypass all of these, so clients reconcile by idempotency key or job ID and never infer rollback from an exit code.

## Available actions and live admission

Every resource get/list item returns `available_actions` with `{resource,verb,enabled,disabled_reasons,destructive,requires_confirmation,required_flags}`. Disabled reasons use `{code,message,gate,source_capability_id}` and implement the map's **Preconditions and disabled reasons** column. Return all applicable reasons, not the GUI's first hidden button. Missing key, quota exhausted and failed usage probe are distinct; do not reproduce “Needs Hubcap key” for every failure. Availability includes implemented/refactor/owner state and read-only session policy. Describe links these reason codes back to ledger IDs.

Separate presentation predicates (panel open, hovered, has Details object, current page, selected card) from required domain facts. CLI identities/input replace presentation state; busy, valid source, writable Steam, installed game, inactive preset, parent ID, key, quota, current hashes and selected installation remain real gates. Revalidate all domain facts at commit and immediately before the applicable service action. GUI visibility and stale CanExecute notifications never confer authority.

Examples: `fix.apply` returns GAME_NOT_INSTALLED, FIX_ALREADY_APPLIED, JOB_ACTIVE, LOGIN_REQUIRED only for lua.tools, EXECUTABLE_WORKFLOW_DISABLED and QUOTA_EXHAUSTED as applicable. Online-Fix lookup is anonymous; it does not ask for an Online-Fix password. `preset.delete` returns PRESET_ACTIVE; `depot.update --enabled false` returns BASE_APP_REQUIRED for base declaration. Depot plans distinguish NO_VERSION and NO_DECRYPTION_KEY; a missing local manifest is fetchable and is not itself a disabled reason. Low disk is a warning in the GUI picker but must be a live run-time precondition as the service already checks. Steam-path invalid, context changed and lock/write failure remain explicit. Status read failure is an error/warning, not a made-up “Loading…” forever.

The bridge's plugin-context gate is not a CLI gate. The 22 retained routes are all cross-referenced in the map. Four have no current caller: POST /check-sources/{appid} maps to source list, POST /download/{appid} to game add, GET /download-status/{appid} to download list/job data, GET /api-list to source list --legacy-index. Their CLI status is mapped or needs-refactor according to the shared operation, with legacy provenance explicit. Do not preserve fabricated 0/100 byte counts, stale route dictionaries or source/apiName ambiguity in the new schema. Calling HttpServerService.DispatchAsync wholesale would require plugin opt-in for all reads and expose UI routes; it is forbidden. Reuse its underlying services through typed methods instead.

## Jobs, events and process lifetime

Use the actual `DownloadItem.Id` for queued downloads. Admission replies promptly with that ID; retain active-key semantics: `manifest:<appid>` across sources, `dlc:<appid>`, `depot:<appid>`, fix/provider/slot and `tool:<name>`. An active duplicate returns its existing ID and `deduplicated:true`; conflicting payload/source is reported rather than silently changing it. The same request ID with identical canonical payload returns the original acceptance even after active-key dedupe no longer applies; a changed payload under the same ID is `REQUEST_ID_CONFLICT`.

A GUI-hosted operation registry wraps existing nonqueue workflows (local sequential drops, DLC check/apply, OAuth, Cabinet sync, mode/plugin/tool/update operations) with IDs and typed results. It does not invent a second scheduler or reimplement their logic. Parent operation IDs expose actual child queue IDs; local batch jobs expose ordered per-file results and one-at-a-time decisions. Serialize local batches to fix the current reentrant VM queue replacement risk. DLC check creates a read-only observational handle; DLC apply is a separate mutating job using a verified check generation. If underlying work cannot safely cancel, return CANCEL_UNSUPPORTED in available_actions; never expose a fictitious cancellation path for mode/plugin/Steamless.

Wire state names are `queued`, `downloading`, `awaiting_confirmation`, `installing`, `paused`, `verifying`, `completed`, `failed`, `cancelled`; wrappers may add `checking` and `running` with a kind. Return raw bytes/total nullable, progress nullable, rate, ETA nullable, timestamps, output path, pending decision, cancel_requested, terminal outcome and warnings. `job get` is read-only and survives successful queue-row auto-dismissal within registry retention. `job wait` subscribes without occupying the dispatcher or blocking admission; it returns promptly with CONSENT_REQUIRED if a pending decision requires new input. `job confirm` requires ID, decision and fresh plan/version; replace requires explicit --yes, skip is an explicit decline. Downloads skip terminates acquisition; local skip continues the next file. Do not confuse local Skip with cancel-whole-batch.

`job cancel` defaults `--keep-files`, equivalent to No in the depot GUI's Yes/delete, No/keep, Cancel/continue dialog. `--delete-created --yes` means Yes/delete, only after completion and only the service's tracked created files/marker/empty ancestors inside the output root. With no submitted command, Cancel/Escape simply does nothing. Preserve already installed bytes and completed DLC. Current data install can ignore cancellation after the install gate: expose cancel_requested separately and report actual final state, with `CANCELLATION_TOO_LATE` warning when completed. Do not promise cancellation is rollback. Retry creates a new ID/tail position and retains old history; repeat quota use requires a fresh plan/consent. Pause/resume is depot-only, retains bytes, validates interrupted files and skips finished depots only within this host lifetime. It is state-changing even when no bytes are downloaded by the pause call itself.

Accepted jobs survive client disconnect, client timeout or Ctrl-C. Request cancellation before admission prevents acceptance; after admission it only detaches observation. Clean GUI exit cancels active/paused work and records Interrupted as current queue history does. Crash cannot guarantee a terminal record. Queue delegates, staging decision continuations, DLC snapshots and depot resume bookkeeping do **not** survive GUI restart. Only existing terminal history (normal cap 100) and installed/persistent app state survive. The registry retains terminal operation/decision results for 24h or 1000 entries, whichever bound is hit first; history eviction can shorten queue lookup after restart. No automatic restart/resume/retry is promised.

Add a host-owned bounded request acceptance journal to prevent lost-ack duplicate quota charges: request ID, canonical payload digest, instance, accepted job/operation ID, timestamp and terminal summary only, no secret payloads. Atomically record an intent before scheduling, then acceptance; a crash between records is `OUTCOME_UNKNOWN`, never an automatic replay. Retain 7 days/10000 entries with explicit expired result. A restarted owner can return history or unknown outcome, not reconstruct delegates. This journal is an implementation requirement for write phases, not something current history already provides. GUI and CLI operations share one conflict-aware coordinator for vault/live/appinfo/settings changes; a pipe alone does not fix in-process races across different existing services. Dedupe journal and per-target locks must not serialize unrelated reads behind a long job.

`download watch` and `activity-log watch` are bounded NDJSON streams of the same four-key envelopes, each containing `data.event` with event ID, instance, cursor, UTC time, category, kind, job/request ID if known, raw state and redacted payload. Queue events observe item PropertyChanged/collection changes, not only ActiveCount StateChanged; progress is coalesced at roughly 100ms and completion/decision is never coalesced away. AppEventLog needs a post-redaction publication hook; it has no subscription API today. The GUI event adapter reads history/JSONL itself and emits redacted new events. CLI never tails files.

Keep AppEventLog's retention: hourly full stream 24h (max 25 segments), daily warning/error stream 7d (max 8), 1 MiB each, next-segment dropped count. Warn events duplicate across current files, so assign an origin event ID before dual append and dedupe merged history; old records lacking IDs use segment identity and explicit overlap handling, not message text alone. A severity-filtered list can read only the appropriate source stream rather than double counting. New queue correlation fields must preserve existing redaction for URLs, tokens, account/profile IDs and long keys. No subscription publishes pre-redaction messages.

Each watch has a 512-event bounded buffer and cursor. On overflow emit GAP with last recoverable cursor and require resnapshot; never grow memory indefinitely or block the GUI/logger on a slow consumer. Heartbeat every 15s reports instance/cursor, no state mutation. Reconnect re-authenticates; an instance change or expired retention returns RESET_REQUIRED. Event history is diagnostic, not the authority for a successful install. `job get`/history reconciles truth after stream gaps.

## Planning, confirmation and gates

`--dry-run` calls the same coordinator's plan stage, returns exact targets, existing hashes, recovery copy evidence, current gates/disabled reasons, estimated quota/bytes (unknown explicitly), prospective writes/process actions/sharing and classification. It does not enqueue, download an archive, generate paid DLC, request missing manifests, validate a new Hubcap credential remotely, pair a device, stage an updater, create a destination, persist a launch rebase, sync/adopt/delete a Default, enable a setting or launch Steam/browser. It may parse/hash submitted bytes and read existing GUI-owned state; optional public metadata probes are declared and cannot consume download quota. Input staging after explicit file submission is transport scratch only, promptly removed for dry-run and never confused with an app mutation. Planning a credential operation checks shape and destination; live validation occurs only with explicit consent.

Plans expire after five minutes and bind command/input digests, instance/selected Steam, target hashes and relevant settings/auth version. Commit rechecks; a changed target/context/policy is PLAN_STALE with a new plan, not an implicit retry. For remote downloads before bytes are known, plan discloses quota spend and the potential overwrite before acquisition. Default no-yes clients get CONSENT_REQUIRED before quota is charged. `--yes` permits the described acquisition and candidate overwrite; after download, a materially different target/hash/effect requires new consent, and refusal cannot refund quota. A GUI or TTY user can then review the real diff. No silent skip-confirmation via legacy VM `silent` calls. Local files permit exact pre-acquisition diff. DLC generation/force-locked manifest paths currently silently overwrite: shared admission must cover them too, even when a diff is unreadable; never fail open because parsing failed.

Every submitted mutation needs explicit consent: an interactive TTY prompt defaults No and summarizes effects; under no-input return a plan unless --yes or the operation is an explicit decline/revocation with a documented safe atomic contract. The CLI prompt is local; no pipe handler opens a MessageBox or steals GUI focus. GUI callers continue their current dialogs but send the same typed plan/decision to the coordinator. `--yes` maps OK/Replace/Revert/Yes to that plan, including the clear-history default-No dialog; it does not blindly click any future modal. One plan can cover all explicitly supplied game IDs/files; return per-target failures instead of erasing successful effects. API consumers may never confirm another request's pending action by guessing an App ID; use its job and plan IDs.

Headless gates are operation-specific:

1. **Steam closed/process consent:** manifest/Lua/DLC installs and fix apply/revert have no blanket Steam-closed gate today; preserve that and return locked-file errors. Managed mode selection requires the shared ModeViewModel stop/install/start sequence. Plugin service and launch-options apply stop/restart selected Steam internally. If Steam is running, require explicit --restart-steam and --yes before reaching those services, otherwise STEAM_RUNNING. A closed instance satisfies the write precondition; never kill unrelated installations/sessions. Preserve restart semantics deliberately: plugin/launch restart only if initially running; mode currently starts even when initially closed, including Custom. Disclose mode's start action in its plan and require consent; fix its gated-failure unnecessary shutdown by checking gates first. `steam restart --yes` explicitly authorizes its verb. CloudRedirect update can require manual closure for a locked DLL; it never implicitly stops Steam. Request new process consent before any future coordinator-managed close.
2. **Executable consent:** `IsExecutableWorkflowEnabled` is false-by-default, unknown-deny, evaluated before acquisition and again before apply/run, including queued work after revocation. Mapping is DenuvoFix to ExecutableGameFixesEnabled; BST/OST, LuaToolsPlugin/Frontend, DepotDownloader, Steamless, SteamAutoCrack and CloudRedirect/Addon to their existing settings. CLI flags, --yes, onboarding and cloud-save commands never grant it. Human enables it in GUI Settings. Revocation/disable, plugin uninstall and fix revert do not require enabling it. Dependency acquisition/run continues quarantine, digest/receipt and user-authorization checks; game fixes retain their own immutable archive/path/CRC policy, which does not certify executable publisher trust. No new HTTP destinations are needed for pipes; all service HTTP remains under OutboundNetworkPolicy.
3. **Hubcap:** distinct personal key, valid `smm_` format, stats success and CanMakeRequests/remaining quota required. Missing, rejected, expired, unavailable and exhausted are separate codes. A source stats read is No; actual download can spend daily quota even if install is later refused and is Irreversible. Key provisioning does not log/query-echo the URL credential. Never switch secretly to a paid source after a failed public source; auto ordering matches the shared GUI/source policy, and its potential quota must be consented.
4. **lua.tools login/quota:** standard sources and lua.tools fix/manifest paths require the GUI's valid session; source checks, SteamML/DexLua guest paths, some guest DLC and Online-Fix lookups/downloads remain public. A missing login returns LOGIN_REQUIRED with instructions; it never opens browser automatically or leaves a queued job waiting for a password. Quota badges are not authority; handle live server limits. Retry and legacy DLC can spend quota again. Public/local DLC batch items continue after a legacy daily limit per DlcBatchService.
5. **Installed game/content/path/space:** fix executable application requires a current installed directory and unapplied slot. Recheck archive membership for Online-Fix Fix Repair. No arbitrary execution, decryption-key dump or unsupported base-depot disable. Lua/ZIP/manifest validation, reparse rejection, bounded decoding/expansion and identity checks remain unchanged in existing services. Steamless preserves first-original .bak; depot download validates key/manifest/free-space and uses anonymous Steam transport, not human Steam credentials.
6. **Cabinet/cloud/helpers:** Cabinet-enabled/connected/engine ownership/busy gates are independent from lua.tools and executable opt-ins. Sync now triggers the local fingerprint/playtime/cloud scheduling path; it is not a guarantee of immediate remote save synchronization. Explain that connected presence/progress and real Steam playtime credit cannot be undone. Cloud saves require already-human-enabled CloudRedirect consent plus OST/BST and configured connection. Never emulate the current OfferCloudSaves closure's consent-setting side effect. FriendLabels false is unsupported; do not falsely report disabled. Update apply requires no active Cabinet helpers and the stronger explicit job-drain lifecycle policy.

Whole-map Destructive? uses maximum possible effect; dry-run returns branch-specific severity. New data install with no overwritten bytes may be Yes, but quota or unbacked overwrite makes it Irreversible. Deleting a live file is Yes only when an exact intact app recovery copy is proven; an arbitrary retained vault is insufficient. `LuaVault.UpdateVariant` deletes old content-hash bytes, and SyncDefaultFromLive can discard old Default. A preset Apply captures outgoing live bytes but can still discard an earlier Default, so its current worst case is Irreversible. Downloaded fix archives with backups are normally reversible file operations, but lua.tools quota is not. No classification treats executable workflows or Steam termination as read-only.

Launch editing uses atomic command inputs, no singleton GUI buffer. `launch-option create/update/delete` persists a staged desired list, validating trim/blank executable/order and the eight exposed fields (executable, arguments, working directory, description, OS list, type, beta key, DLC gate). Position changes compact indices. Source identity/OsArch are preserved internally, not invented editable fields. Whole-list update --apply false is Save then Cancel at “Apply now?”; --apply true additionally applies/restarts with explicit process consent. `launch-option apply --drifted` is the existing reapply intent, not a fabricated GUI button. Fix Restore's record deletion on Apply failure in the shared coordinator, then remove the current Irreversible warning only with evidence that a retry/restore remains available. Do not copy singleton stale-buffer state or failed-load Restore visibility into admission.

## Auth, credentials and pipe boundary

Agents never receive, request, store or enter a human's password. Account login --browser starts the existing Discord PKCE/local callback operation only when explicitly requested; the human authenticates/authorizes in their browser. No-input automation receives HUMAN_ACTION_REQUIRED/job ID and may wait for the human without a modal; it must not drive their password form. The five-minute browser callback timeout remains. Account login --code-stdin accepts a human-provided six-character alphanumeric Discord /login DM code (single-use, five-minute expiry), never command-line/env/history text. Do not require a new raw session-token injection API: the single GUI already owns AuthService, its DPAPI auth.dat and serialized refresh. The inventory's independent-headless token gap is resolved by IPC plus existing provisioning, not token export/import. Transient/offline session behavior stays with AuthService.

Hubcap provisioning accepts its key through dedicated stdin/secret frame or an explicitly secured secret-file handle; it validates/stores through the shared key coordinator and never returns the saved value. Cabinet uses the same secret channel for the normalized pairing code or legacy credential-bearing link; the server origin is a separate visible argument, HTTPS-only. Keep pairing POST's required matching Origin and existing redirect/cookie restrictions. Pairing includes device data and /api/me verification, uses the Cabinet engine thread/ownership, and may establish ongoing presence/progress sharing. No silent cloud-save enrollment follows connection. Disconnect/logout clear local credentials, do not remotely revoke or erase published data. Use per-request private buffers, clear secret material promptly, and exclude it from request journal, session transcript, errors, telemetry and logs. Secret field names are always denied by --fields; setting summaries show configured/status/expiry only. A Lua may embed addtoken/depot keys: --content returns redacted/parsed public content plus a content version hash; full-fidelity mutation requires an explicit user-supplied file kept outside agent stdout. Diff output never includes key material.

Pipe security is an independent local capability, not the plugin/account/Hubcap token:

- Acquire the existing application-owner mutex before publishing a server. Enforce one per-user writer across sessions before enabling mutations (D2); per-session pipe naming alone cannot protect shared AppData. Normal host is unelevated. Reject unsupported simultaneous owner sessions rather than create another container/profile implicitly.
- Identity includes fork, protocol major, Windows SID and session/instance. Use a random pipe name, CurrentUserOnly on client/server, explicit Windows account/elevation checks, and server-side remote-client rejection. Connect only to local machine; verify peer PID/start identity, session and elevation as well as SID. Never widen ACLs for convenience. BCL P/Invoke to Windows pipe/token/DPAPI APIs is acceptable where managed APIs cannot express reject-remote or DPAPI without an extra package; no new NuGet dependency or GUI reference enters the client.
- Generate 256 random capability bits per owner lifetime. Discovery is an atomic owner-only local record with protocol, PID/start identity, nonce, random name and DPAPI CurrentUser-wrapped capability, protected directory/record ACLs and no inherited broad write/read access. Validate canonical paths/reparse safety/ACL/owner before reading or replacing. Discovery is the only app-owned file the CLI reads; never traverse to adjacent state. Client unwraps with Windows DPAPI API; no plaintext substitute. Remove on clean exit, rotate on restart/update, validate stale/spoofed descriptors before connection. Missing/stale owner is GUI_NOT_RUNNING; invalid ACL/capability is security failure, not a recovery write.
- Authenticate capability inside the bounded pipe handshake, compare decoded bytes in constant time, never send it in argv/env/stdout/logs. Verify server identity **before** disclosing the capability or credential frames. Client capabilities are not isolation from malicious code already running as that same user: such a process can normally discover/decrypt it. ACL/account/elevation/remote rejection defines the real boundary.
- Use little-endian uint32 length-prefixed UTF-8 JSON control frames, maximum 64 KiB, maximum 1 MiB paginated result frame negotiated separately; malformed/zero/oversized/unknown-field input fails closed. Strict protocol schemas/argument validation, request deadline and correlation IDs apply. Explicit bounded binary chunks for --file use a separate authenticated upload state with declared total/digest and no arbitrary RPC operation during upload. Control auth precedes body processing. Maximum 16 active connections, 16 outstanding requests/connection and 32 new accepted operations/instance pending admission; excess returns BUSY/retry-after. Enforce per-connection five-second idle/read/write deadlines outside authenticated watch/wait heartbeats. Each connection gets independent cancellation so one stalled peer cannot wedge acceptance. Backpressure is admission, not a new download-concurrency scheduler; existing GUI queue currently starts every download and serializes only installs.
- Requests include protocol version, expected instance and selected Steam identity. Reject context/version mismatch; never use caller environment to change the selected installation. Reconnect/discover on GUI restart/update and re-authenticate. Major mismatch is unsupported; minor versions negotiate optional fields, never assume an unimplemented mutation. A request journal resolves lost acknowledgements; reconnect never blindly resubmits quota-consuming work.

Absent GUI means bounded structured failure, no prompt or direct state inspection. `application start` is reserved, not a hidden fallback. Any future approved start must launch the trusted signed GUI with --minimized through existing single-owner startup and wait for authenticated readiness; no separate headless host, command before owner mutex, or unpumped Dispatcher.CurrentDispatcher. Running GUI/tray is the actual owner and its persisted/background effects continue. Explicit GUI shutdown/update breaks the pipe; reply with a scheduled lifecycle receipt before shutdown, then require rediscovery. Current update checks do not depend on CLI plugin consent, and a plugin check remains purely local bundled-loader status; full update check may stage signed app artifacts but never auto-apply.
