## Security conclusions

No remote signature-verification bypass or unsigned package execution path was identified in the reviewed code. This is a scoped static conclusion, not an unconditional security certification. Shipping remains contingent on final tests, release workflow validation, and the maintainer's custody of the matching private key.

- **Signature fails closed.** [VerifyManifest](../src/LuaToolsGui/Services/UpdateService.cs#L40) bounds raw manifest/signature sizes, verifies exact manifest bytes using the embedded ECDSA key, SHA-256 and 64-byte IEEE P1363 encoding before JSON interpretation. Missing/invalid keys or signatures abort. The public key is an embedded application resource, not downloaded configuration. Repository, `1.4.N` version shape, fixed asset name, size, hexadecimal commit and SHA-256 are validated. The internal test-key constructor is not user configuration.
- **Network metadata cannot authorize code.** [CheckAndStageAsync](../src/LuaToolsGui/Services/UpdateService.cs#L113) constructs fixed fork metadata URLs, verifies the manifest before requesting the ZIP, and constructs the package URL from constrained signed fields. No manifest-controlled arbitrary URL exists. Metadata is limited to 16 KiB/64 bytes, the ZIP to 256 MiB. `AppHttp` disables automatic redirects/cookies/proxy and applies destination/redirect validation with at most five hops and bounded response bodies/time. Redirects can use the application's broader HTTPS host allowlist, rather than a dedicated update-only allowlist; package execution still requires the pinned signature and hash, and updater requests carry no credentials.
- **Rollback is constrained by authenticated state.** Staging requires a version above both the running assembly and the remembered, signature/hash-verified approved package. [Bootstrap](../src/LuaToolsGui/Services/UpdateService.cs#L253) also requires a version above the launcher assembly and re-verifies package authenticity. Version claims from an unsigned pointer alone cannot pass. The approved pointer accepts only a GUID, not an arbitrary path. Local deletion/replacement of remembered state is explicitly outside the rollback boundary. `1.4.0` developer builds skip network update checks; CI overrides release version to `1.4.N`.
- **Extraction rechecks exact bytes.** [ExtractVerified](../src/LuaToolsGui/Services/UpdateService.cs#L79) authenticates the ZIP, reopens and rehashes it under the same write-denying file handle used for extraction, rejects an existing output directory, and writes into a fresh GUID directory. It rejects traversal, roots/drives/ADS, invalid Windows names, duplicate paths, symlink/reparse entries, empty path components, trailing spaces/dots, and excessive entries/aggregate declared expansion. The package must include the root executable. Changes to a cached ZIP fail hash verification instead of substituting its executable. The signed publisher remains trusted for all DLLs/configuration inside the signed package.
- **Launch is direct and explicitly approved.** [App startup](../src/LuaToolsGui/App.xaml.cs#L244) stages in the background and offers the Restart action; `ApplyOnExit` does nothing. [ApplyAndRestart](../src/LuaToolsGui/Services/UpdateService.cs#L193) atomically writes the approved GUID pointer, re-verifies/extracts, launches the fixed executable without a shell, restores the previous pointer if launch fails, then shuts down. [Program](../src/LuaToolsGui/Program.cs#L16) waits at most 30 seconds for the predecessor before acquiring the ordinary single-instance mutex. Future shortcut launches reauthenticate and extract the approved package rather than trusting an old mutable executable cache.
- **Filesystem defenses were revised during review.** Initial missing reparse checks, mutable pointer publication and unbounded ordinary run/package accumulation were reported to the implementation agent. The reviewed snapshot checks root, metadata, ZIP, pointer, extraction destination and cleanup paths; pointer publication uses create-new temporary bytes, disk flush and atomic move. Cleanup retains two newest GUID directories plus current active/pending/running directories and recursively refuses unsafe paths. These revisions address the initially observed routine path/state hazards without claiming OS isolation from malicious code running as the same user.

## Remaining findings and limits

**Medium, local attacker limitation — extracted executable tree is mutable before launch.** ZIP verification/extraction is protected against changing the authenticated input handle, but output files and parent directories remain writable by the current Windows user. A concurrent same-user process can replace the freshly extracted executable/dependencies or race path checks. This is explicitly documented in [RELEASES.md](../RELEASES.md); it is not an internet-feed signature bypass. Running a writable application with elevated rights would cross a more serious boundary and is not part of the reviewed updater's launch behavior. Stronger defense would require OS-enforced protected installation/storage and a separately designed privileged installer.

**Low, availability — no caller cancellation and synchronous restart extraction.** Downloads have central body deadlines and a five-minute HttpClient timeout; the service does not accept the app's shutdown token. It can continue staging while shutdown is underway. Restart signature/hash/extraction and startup bootstrap execute synchronously, including up to a 1 GiB declared expanded package, so the UI/startup can pause on large or slow disks. The semaphore uses nonblocking acquisition and `finally` release; no lock/wait cycle or obvious deadlock was found. The dispatcher callback is a synchronous toast notification, not a wait on the update gate. Add lifecycle cancellation and background preparation if these pauses are unacceptable.

**Low, availability — retention is best effort.** Cleanup retries locked/unsafe directories on later launches; its retention count is not an absolute disk quota. Partial extraction and cleanup failures can leave data behind. A hostile same-user process can deliberately prevent cleanup. Ordinary successful iterations are pruned; broad claims of a hard total disk bound would be inaccurate.

**Operational trust — signing and release authority.** [Signing script](../scripts/sign-release.ps1) checks fork/branch identity, validates version/commit shape, hashes a bounded package, signs exact UTF-8 JSON and verifies the signature against the embedded public key before emitting files. [.github/workflows/build.yml](../.github/workflows/build.yml) gates release on the build/test job, checks out the workflow commit, derives a commit-count version from baseline ancestry, verifies current branch tip, skips existing versions, uploads a draft release and then publishes. Matching signature proves possession of the key; it does not independently prove benign source or build reproducibility. Write access to the trusted branch/workflow and private-key custody are release authority. No GitHub secret values, branch protections, actual release assets, or matching private-key possession were verified by this reviewer. Root owns final CI validation and release authorization.
